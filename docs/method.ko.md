# 장표 작성 방법론 (한국어 원문)

> 영어판: [method.md](method.md). 이 문서가 원문이고, 두 문서가 다르면 이 문서를 따른다.

장표 일은 **이 순서와 형식을 벗어나지 않는다**. 도구(Figma/PPTX)는 바뀌어도 방법은 같다.

## 1. 기획의 순환과정 — 단계별 원칙과 산출물
회의실과 목표·독자를 정한 뒤 생각박스부터 검토까지의 순환을 거쳐 보고서를 만든다. 검토 결과를 반영해 **생각박스부터 되풀이**한다.

| 단계 | 원칙 | 산출물 |
|---|---|---|
| 회의실 | 회사 서식이 있으면 먼저 분석해 레이아웃·색·글꼴·글자 크기를 맞춘다. 없으면 기본 템플릿(팀이 정한 Figma 슬라이드 양식)을 쓴다 | 형식자료가 준비된 작업용 PPTX(또는 Figma 작업 프레임) |
| 목표·독자 | 발표용 덱과 읽기용 덱을 구분한다. 합의되지 않은 용어는 도입부에서 정의한다 | 목적·독자·핵심 메시지 합의, 전체 분량 |
| 생각박스 | 쪽지는 작성자별 색으로 붙인다. 만드는 방법은 형광 스티커, 내용은 회색 메모로 나눈다 | 작업대의 쪽지와 메모 |
| 고스트덱 | 제목 영역만 읽어도 이해되게 쓴다. 보고서체, 이름으로 부르기, 수에는 기준을 붙인다 | 장별 제목 영역 문장 |
| 딱지장표 | 문장 없이 자리·역할·관계만 놓는다. 관계 → 먼저 검토할 구성 → 전략 표현 순서로 고른다 | 관계 배치 스케치 |
| 개별 구현 | 네이티브 객체, 테마 색, 안내선 안에서 만든다. 글자를 줄이기 전에 문장을 정제한다 | 보고용 슬라이드 |
| 검토 | 수행·가능·기대·검증을 구분한다. 지적받은 오답은 오답 사례로 모은다 | 수정본, 오답 사례 기록 |

실무 적용: 장표 요청이 오면 1~5 단계를 **글(마크다운)로 먼저** 만들어 요청자와 맞춘 뒤(목표·독자 한 줄, 장별 제목 문장 목록, 장별 관계 스케치 한 줄), 그 다음에만 개별 구현에 들어간다. 제목 문장 목록 없이 바로 그리지 않는다. 이 글은 `jobs/<job>/PLAN.md` 에 남긴다(예시: [examples/PLAN.md](../examples/PLAN.md)).

## 2. 장표 한 장의 형식
- **제목 = 결론 문장**(명사 나열 금지), 바로 아래 **한 줄 근거/설명**(보고서체, 10~11pt 회색).
- **제목은 한 줄**로 쓰고 본문 폭 오른쪽 끝까지 채운다. 글자 크기를 폭에 맞추고(1920 프레임 기준 약 40~52px), 가장 큰 크기에서도 짧으면 문장을 늘린다. 줄바꿈으로 두 줄을 만들지 않는다(`scripts/fit-headline.js`).
- 본문은 **왼쪽 행 라벨 열**(회색 배경, 굵게: 검사자/대상/확인 항목/결과 처리, 원칙/산출물) + 오른쪽 내용 열. 비교 구조면 열마다 머리띠, **강조할 열 하나만 진한 강조색**(기본 예: 진청 #2E5C7A 계열, 흰 글씨), 나머지는 밝은 회색(#E6E6E6) 머리띠·#F2F2F2 칸.
- 확인 항목은 ☐ 체크리스트. 흐름은 작은 네모(썸네일 → 단계 → 결과) 화살표 도식, 되돌림은 아래쪽 괄호선과 설명.
- 아직 확정 아닌 것은 점선 테두리 **"제안"** 딱지.
- 색은 테마 색만(검정·회색 단계·강조색 1개). 주황(accent2) 위 흰 글씨 금지. 통짜 이미지 슬라이드·그림으로 붙인 표 금지(네이티브 객체).
- 글자 최소 10pt(16:9 1920px 프레임이면 20px, A4 595px 프레임이면 10px). 안내선(여백) 밖 본문 객체 금지.
- 수에는 기간·분모·단위, 사람·회사는 이름으로 부른다.

## 3. 검토 — 형식 검사와 논리 검토
형식 규칙은 기계로 재고, 논리는 작성 문맥을 모르는 독립 검토자가 묻는다. 형식 검사를 통과해도 배치가 관계와 맞는지는 따로 확인한다.

| | 형식 검사 | 논리 검토 |
|---|---|---|
| 검사자 | 기계 — 스크립트와 렌더로 잰다 | 독립 검토자 — 작성 문맥을 모르는 사람(세션)이 묻는다 |
| 대상 | 안내선·글자 크기·색·글꼴·편집성 같은 형식 규칙의 위반 | 제목 영역, 관계와 배치의 일치, 근거 같은 내용의 논리 |
| 확인 항목 | ☐ 엄격 안내선 밖으로 나간 본문 객체 ☐ 본문 10pt 미만의 글자 ☐ 고정 HEX 로 칠한 본문 객체 ☐ 주황(accent2) 위의 흰 글씨 ☐ 통짜 이미지 슬라이드, 네이티브가 아닌 표 ☐ 겹침·넘침 — 렌더 썸네일로 확인 | ☐ 제목 영역만 읽고 결론을 말할 수 있는가? ☐ 배치가 관계와 맞고, 그 독자 질문에 '예'인가? ☐ 나란히 놓은 항목이 같은 층, 같은 종류인가? ☐ 분할·색·강조마다 근거를 한 문장으로 쓸 수 있는가? ☐ 그림이 헤드 메시지를 증명하는가? ☐ 수에 기간·분모·단위가 있는가? |
| 결과 처리 | 새 형식 규칙은 기계 검사로 바꿀 수 있는지 함께 적어 쌓는다 | 검토자는 지적만 하고 고치지 않는다. 지적은 채택·미채택·보류와 이유로 정리한다 |

## 4. 이 레포의 도구로 실행하기
- 형식 검사: `node bin/figma-run.mjs scripts/lint-format.js --node <프레임id> --arg frame=<프레임id>` → 슬라이드별 위반 목록. 렌더 썸네일은 `node bin/figma-api.mjs export … --format png --scale 0.5` 로 같이 본다.
- 논리 검토: `bin/review-logic.sh <job> <key> <슬라이드 id,…>` → 슬라이드 PNG 를 **문맥 없는 Codex 세션**에 주고 위 6개 질문으로 지적만 받는다 → `jobs/<job>/logic-review.md`. 채택·미채택·보류는 작성자가 적는다.
- 금지어 검사: 고객에게 보여 줄 장표는 내보내기 전에 `scripts/scan-words.js` 로 페이지 전체 텍스트·프레임 이름을 검사한다.
- 오답 사례: 지적받은 것은 `docs/errata.md` 에 "장표 · 지적 · 처리 · 새 규칙(기계화 가능?)" 한 줄씩 쌓는다.
- 작성 단계 산출물(목표·독자, 제목 문장 목록, 관계 스케치)은 `jobs/<job>/PLAN.md` 에 남긴다. 구현 위임(`bin/codex-task.sh`)은 PLAN.md 가 확정된 뒤.

## 5. 차트 — 관계에 맞는 종류를 고르고, 한 가지만 강조한다
"직관적으로 그려줘"로 끝내지 말고, **딱지장표 단계에서 관계를 정한 뒤 아래 표로 차트 종류를 고른다**. 막대·꺾은선만 반복하지 않는다.

| # | 차트 | 이럴 때(관계) | 쓰는 법 | 난도 |
|---|---|---|---|---|
| 01 | 파이 | 전체 중 비중, **항목 2~4개만** | 큰 조각에 강조색, 조각 안에 % | 기본 |
| 02 | 도넛 | 비중 + **총합 한 숫자** | 가운데 총합(큰 숫자 + 단위), 오른쪽에 항목·% 표 | 기본 |
| 03 | 퍼널 | 단계별 **이탈** | 왼쪽 단계명·인원, 오른쪽 '전 단계 대비 %', 가장 큰 이탈 단계만 강조색 | 기본 |
| 04 | 와플 | 비율을 **100칸**으로 직관화(사람 수·고객 수) | 10×10 칸, 옆에 큰 % + 설명 + 나머지 수 | 중급 |
| 05 | 트리맵 | **계층의 비율**(카테고리→하위 품목) | 상위 그룹 라벨 위에, 칸 안에 이름·%, 최대 칸만 강조색 | 중급 |
| 06 | 선버스트 | 계층 비율을 **원형으로**(채널→캠페인) | 안쪽 고리 = 상위, 바깥 고리 = 하위, 강조할 가지 하나만 색 | 중급 |
| 07 | 폭포(워터폴) | 시작→끝 **증감 요인 분해**(9월→10월 매출) | 시작·끝 막대는 진한색, 증가/감소는 다른 톤, 막대 위에 +/− 값, 연결 점선 | 중급 |
| 08 | 파레토 | **상위 몇 개가 대부분**인가(상위 20%→80%) | 내림차순 막대 + 누적 꺾은선 + 80% 점선, 80%를 넘는 지점 표시 | 중급 |
| 09 | 마리메코 | **두 비율을 한 번에**(폭 = 채널 비중, 높이 = 기기 구성) | 열 아래 이름·폭 %, 칸 안에 % | 심화 |

고르는 순서: 비중이면 01·02·04(항목 5개 이상이면 막대로) → 계층이면 05·06 → 단계·흐름이면 03 → 변화 원인이면 07 → 집중도면 08 → 두 축 구성이면 09. 시간 추이는 꺾은선, 항목 비교는 가로 막대(긴 순 정렬)가 기본이다.

차트 한 장의 형식:
- 차트 제목 아래 **무엇·단위** 한 줄(예: "9월에서 10월 매출 (만원)", "고객 100명 중"), 범례는 오른쪽 위 작은 네모.
- **강조색은 하나**, 나머지는 검정·회색 단계. 강조는 헤드 메시지가 가리키는 한 칸/한 막대에만.
- 값은 데이터 위에 직접 적는다(축 눈금을 읽게 하지 않는다). 격자선은 옅게, 축 0~최대만.
- 차트 아래(또는 장표 제목)에 **이 차트가 말하는 것 한 줄**("상위 20%가 80%?", "단계별 이탈")을 붙인다.
- 차트도 네이티브 객체로 만든다(Figma 벡터·PPTX 차트). 그림으로 붙이지 않는다. 예시 데이터는 "예시 데이터"라고 표시한다.
- 논리 검토 추가 질문: ☐ 차트 종류가 관계(비중·계층·흐름·분해·집중·두 축)와 맞는가? ☐ 강조색이 헤드 메시지가 가리키는 곳 하나뿐인가?

## 6. 실전에서 쌓인 규칙
- **요청자가 준 흐름을 그대로 쓴다.** 장 번호 목록을 받으면 그 번호·순서·분량을 1:1 로 쓴다. 분량을 맞춘다고 챕터 표지·목차·마무리 장을 끼워 넣지 않는다. 더 넣고 싶은 장은 PLAN 에 '제안'으로만 적는다.
- **양식을 지킨다.** 새 장표도 백지에서 즉흥으로 디자인하지 않는다. 덱 종류(제안서·보고서·강의 등)를 먼저 확인하고 그 종류에 정해진 양식을 복제해 쓴다. 헷갈리면 참고 장표를 요청한다.
- **상태 표시 말을 이름에 쓰지 않는다.** 복제본은 `<job> NN · 제목` 처럼 쉬운 이름으로 부른다. "WIP"·"draft" 같은 말은 페이지·프레임 이름에도 보고에도 쓰지 않는다(남아 있으면 `scripts/strip-name-tag.js`).
- **고객 장표에 내부 이야기를 쓰지 않는다.** 내부 시스템 이름, 내부 처리 과정, 방법론 출처, 쓴 도구·모델 이름, 검증 과정, 전문 약어는 제목·본문·각주·프레임 이름 어디에도 넣지 않는다. 제목은 "고객이 무엇을 주면 무엇을 받는지"로, 받는 것은 구체적인 결과물로 쓴다. 약어는 쉬운 말로 푼다. 내보내기 전에 금지어 검사를 돌린다.
- **약속·숫자는 받은 것만.** 제공물·약속·숫자는 요청자가 준 것만 쓴다. 구체화한다고 지어내지 않는다. 없는 숫자는 `[확인 필요]` 로 남긴다.
- **형식 검사·논리 검토 통과 ≠ 읽힘.** 고스트덱에 "이 장을 본 독자가 무엇을 결정하나" 열을 둔다. 재료(캡처·다른 자료)를 채워 넣기만 한 장은 독자가 결정할 근거가 없다.
- **다른 고객의 자료·가격을 쓰지 않는다.** 사례는 익명(고객사 A·B)과 숫자로만.
- **"~만"·"유일" 주장은 대조한다.** 제목이 "X 만 숫자로 남는다"처럼 배타적이면 표의 다른 열도 같은지 확인한다. 흐름 비교는 줄마다 마지막 상자(도달점) 문구가 같아야 한다.
- **가격·비율은 계산해서 대조한다.** "정상가 A … (-N%)" 같은 문구는 검산한다.
- **그림을 재사용하면 그림 속 라벨과 본문 라벨을 대조한다.**
